## 1. 完成の定義

本番向けの描画処理をC++として実装・検証し、C移植時に計算方法やデータ構造を設計し直さなくてよい状態を目指す。そのため、処理本体には最初からCでも表せる構造体・関数・固定長配列・ループを使う。C++コンパイラで開発しながら、処理本体だけをCコンパイラでも構文確認する。

完成する描画機能は次のとおり。

| 項目 | 完成時の状態 |
| --- | --- |
| 数値 | 合意済みの32ビット整数・Q16.16仕様。演算順、丸め、例外入力の結果を固定 |
| シーン | 固定配列で定義した少数の球と材質。まず球2個から始める |
| カメラ | 固定視点・固定画角。画素中央の1サンプル、乱数なし |
| 基本描画 | 最近傍交差、法線の色表示、背景 |
| 直接照明 | 平行光源1個と一定の環境項 |
| 影 | 光源方向への遮蔽判定による硬い影 |
| 反射 | 粗さ0、最大2回。再帰を使わずループで追跡 |
| 出力 | RGB画素列とPPM。画素値の決定とファイル・UARTへの出力を分離 |
| 再現性 | 同じ仕様・設定で同じ画素列が得られ、数値と画像を自動比較できる |
| 移植準備 | 処理本体がC11の構文検査に通り、C++固有の実行時機能を必要としない |

現在の教材用C++版は、学習と実装比較のために保持する。ガラス、粗い金属、煙、画像テクスチャ、Perlin、被写界深度、モーションブラー、複雑な箱・変換は今回の完成条件に含めない。BVHは物体数を増やした後の実測で判断し、最初は総当たりを使う。

「C++版の完成」と「RV32IM・自作RTLでの動作確認」は別々に記録する。C移植で機械的に移せるようにする対象は描画・数値計算の本体であり、UART、リンカ設定、起動処理などの環境対応は別作業として残る。

## 4. 各段階で行うこと

### CPP-00：比較できる出発点を作る

目的は、今後の変更を既存の実装に対応づけられるようにすること。

1. 現在のコミット、未コミット差分、比較対象のコミットを記録する。
2. `feat/tests-cpp` のルート直下のファイルと、現在の `sw/raytracer/cpp/` のファイルを対応づける。
3. 差分を「元の固定小数点処理」「教材から追加した機能」「固定小数点で必要な対策」「構成・書式だけの違い」に整理する。
4. 構成・書式は、機能・丸め・乱数の消費順を保てる部分から元の実装に合わせる。球の交差計算など、固定小数点の範囲対策が必要な処理は理由を記録して保持する。
5. `main.cpp`、`ppm.cpp`、`week2.cpp` を別ターゲットとしてビルドする。設定変更が必要なものは検証用コピーを使い、まず16×9または32×18で出力を確認する。
6. 画像ファイルが必要な経路は、使用する入力を確定してから検証する。入力がない状態の起動失敗も記録する。

完了条件は、再現コマンド、設定、出力PPM、ハッシュ、失敗した条件が揃うこと。ここで保存する画像は「現行実装の比較用」であり、最終仕様の正解画像とは分ける。

### CPP-01：C移植で結果が変わらない数値規則を決める

次の項目は、方針書の推奨をそのまま正式仕様として実装せず、最新版の言語仕様とチームの合意を確認する。

| 決めること | 必要な確認 |
| --- | --- |
| 乗算の丸め | raw値 `-1 × 1` が現行の0か、Floorの−1か |
| 内積の丸め位置 | 各積を丸めるか、3項の積和後に1回丸めるか |
| 逆数・逆平方根 | 許容誤差だけでなく、全実装が同じraw値を返す規則 |
| 例外入力 | ゼロ除算、負数平方根、正規化するゼロベクトル、表現範囲外 |
| 中間値とオーバーフロー | ラップ・制限・入力制約のどれを使うか。C/C++の未定義動作に依存しない実装 |
| 除算の扱い | `fpm_div` を残す場所と、将来NESVへ移す演算手順。逆数乗算との違い |
| データ配置・出力 | 配列要素の幅、RGBの順序、行順、クランプ、ガンマ変換 |
| 交差の境界 | 接線、最小・最大の `t`、同じ距離の物体の選択、自己交差回避 |
| 64ビット演算 | 本番での利用可否、必要な補助ルーチン、RV32IMでの生成コード |

数学関数の名前は既存実装とチームのAPIを照合して決める。`qmul`、`dot3`、`qsqrt`、`qrcp`、`qrsqrt` に相当する共通テストを用意する。検証用の広い精度で期待値を作る処理と、本番の数値処理を分離する。

合意前は現行仕様を「暫定」として記録できるが、最終的な基準画像やC移植の数値一致を完了扱いにはしない。

### CPP-02：C++の段階で移植時の設計変更を済ませる

本番向けの処理本体には、次の形を採用する。

| 現在のC++表現 | 本番向けC++版で使う形 |
| --- | --- |
| メンバ関数・演算子を持つ `vec3` | データだけの構造体と `vec3_add`、`vec3_dot` などの通常関数 |
| `hittable`・`material` の継承と仮想関数 | 種別を表す番号、データ配列、通常関数内の分岐 |
| `shared_ptr`・`make_shared` | 配列内の識別番号。実体の寿命はシーン全体で管理 |
| `vector`・`new`・`delete` | 上限を決めた固定長配列と有効要素数 |
| 再帰的な `ray_color` | 現在のレイ・累積色・減衰率を保持する上限付きループ |
| コンストラクタ・例外 | 明示的な初期化関数と戻り値によるエラー通知 |
| 参照引数・テンプレート・ラムダ | 値またはポインタを引数とする、型が明確な関数 |
| `std::cout`・画像ファイル処理 | ホスト側の入出力処理。描画本体は画素値だけを返す |
| 実行中のランダムなシーン生成 | 固定値のシーン定義 |

関数ポインタやC++の所有権管理も描画本体には導入しない。材質は必要な拡散面と粗さ0の鏡面から始める。固定配列の容量、空のシーン、容量超過時の戻り値も定義する。

処理本体のヘッダーは `<stdint.h>` などCと共通で使える形式にする。`constexpr`、`auto`、オーバーロード、暗黙の初期化などを本体の必須機能にせず、同じデータと処理をCでも表現できるようにする。構造体をそのままファイルへ書き出さず、比較・転送するフィールドを明示し、パディングに依存しない。

完成条件は、本体をC++としてビルドでき、同じファイルをC11として構文検査できること。この時点では別のC版を作らず、1つの本体を検査する。

### CPP-03：最小の固定描画を完成させる

- 固定カメラ、画素中央1サンプル、球2個、背景、法線色から始める。
- カメラの基底、画素位置、画像の上下、場面の座標範囲を固定する。
- 球の交差、最近傍の選択、法線、色変換を別々の関数として確認する。
- 正規化後も内積が厳密に1とは限らないため、球交差の係数を安易に省略しない。
- 巨大な床用球をそのまま基準シーンへ移さず、中間値の範囲を確認した小さいシーンを使う。
- PPM出力は描画本体から分離し、画像全体の確保なしでも画素順に出力できるようにする。

既知の交差・非交差・球の内側・ゼロ方向・接線付近・同距離のケースを検証する。小さい画像の代表画素を確認したうえで、繰り返し描画の一致を確認する。

### CPP-04：直接照明を追加する

平行光源1個と一定の環境項を加える。法線と光源方向から明るさを求め、色への乗算順とクランプ・ガンマ変換の位置を固定する。

検証には、光を正面から受ける面、背面、光と法線が直交する面を使う。法線色表示を検証用モードとして残し、照明を追加した画像は新しい基準として保存する。

### CPP-05：硬い影を追加する

交点から光源方向へ遮蔽確認用のレイを出す。遮蔽物が見つかったら判定を終了する。影の中で残す環境項と、遮る直接光の扱いを明示する。

自己交差を避ける位置補正と最小 `t` は、シーンの尺度とQ16.16の刻みに合わせて決める。遮蔽物あり・なし、表面直近、接線付近で結果を確認する。

### CPP-06：最大2回の完全鏡面反射を追加する

反射は乱数・粗さ・再帰を使わず、レイ、反射回数、累積色、減衰率をループ内で更新する。

「最大2回」は、最初のレイに加えて反射後のレイを2本追跡する意味とする。最大3区間を評価し、2回反射した先の表面または背景まで確認する。遮蔽確認用のレイは反射回数に含めない。

上限に達した鏡面での終了色も実装前に固定する。案として、以後の反射寄与を0として、それまでに得た色を返す。材質ごとの局所照明と反射色をどう合成するかも合わせて定義し、C移植時には変更しない。

検証には、背景を映す鏡、物体を映す鏡、2回反射する配置、向かい合った鏡を使う。反射方向・減衰・最大区間数・必ず終了することを確認する。

### CPP-07：C++版を完成判定する

サイズ案はMicro＝32×18、Tiny＝80×45、Full＝160×90。チームに既存の定義があればそちらを優先する。まずMicroを通し、次にTiny、最後にFullを検証する。

- 合意済みの数値テストベクトルとraw値が一致する。
- 法線色・直接照明・影・鏡面反射の各段階に、設定と対応づけた基準画像がある。
- 同じ条件でRGB画素列が再現する。比較失敗時は最初に違った画素と必要な中間値を示せる。
- 最適化あり・なしで数値と画像を比較し、ホスト上の未定義動作検出を通す。
- 本体がC++ビルドとC構文検査に通り、再帰・ヒープ・仮想関数・C++実行時ライブラリへの依存がない。
- コード、固定配列、作業領域、スタックの見積りと、利用可能な対象ビルドのリンク結果を記録する。
- 利用可能なら、本体をRV32IM向けにコンパイルし、命令・ABI・補助ルーチンを確認する。未実施の場合は「ホストC++版完成、RV32IM確認待ち」と明記する。
- ビルド・実行・比較のコマンド、コンパイラ設定、数値仕様の版を記録する。

基準画像は、既知の小例と数値テストを確認してから採用する。変更した実装の出力で正解画像を自動的に上書きしない。数値仕様や描画機能を変更した場合は、画像の版も更新する。

## 6. Cへ移すときの作業

C++版の完成後は、次の作業に限定できることを目標にする。

1. 処理本体をCのソース・ビルド対象へ移す。
2. ヘッダー、外部シンボル、定数定義、初期化、Cコンパイラの警告を確認する。
3. ホスト側の入口をCの入出力へつなぐ。RV32IMでは同じ画素出力を対象BSPのUARTへつなぐ。
4. C++版と同じ数値テストベクトル・シーン・画素条件を実行する。
5. 数値のraw値と復号後のRGB画素列が完全一致することを確認する。

この段階で球交差の計算式、丸め、再帰の除去、材質の持ち方、シーンの保存形式を改めて設計する必要があるなら、CPP-02またはCPP-07の完了条件を満たしていないと判断する。

PPMのP3とP6でファイル表現が違う場合は、ファイルのハッシュではなく復号した画素列を比較する。RV32IM実行・RTL一致・サイクル測定はそれぞれ別の結果として記録する。
